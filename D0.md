# D0 — Análisis del Sistema: Minimarket "La Esquina"

**Documento de requerimientos funcionales y reglas de negocio**
**Versión:** 1.0
**Fecha:** 2026-10-23
**Rol:** Analista de sistemas
**Estado:** Para revisión

---

## 1. Descripción del problema

El minimarket "La Esquina" no cuenta con un sistema que registre ventas ni controle el inventario, lo que ocasiona desconocimiento de las ventas diarias y quiebres de stock por depender de un registro manual en cuaderno y la observación visual de los estantes.

---

## 2. Usuarios, responsabilidades y proceso actual

### 2.1 Usuarios identificados

| Usuario | Responsabilidades en el sistema |
|---------|---------------------------------|
| Administrador del minimarket | Registrar y mantener productos (datos, precios, stock). Consultar el listado de productos e identificar alertas de stock mínimo. |
| Vendedor / Cajero | Registrar las ventas de los productos. Consultar las ventas del día y el total vendido. |

> SUPUESTO: El minimarket tiene al menos una persona que cumple el rol de administrador y una o más personas que actúan como vendedores. Ambos roles comparten el acceso al sistema sin autenticación (fuera de alcance).

### 2.2 Proceso actual

El flujo operativo actual del minimarket es el siguiente:

1. **Registro de productos:** No existe un catálogo formal. El administrador conoce los productos y precios de memoria o por notas sueltas.
2. **Control de inventario:** El administrador revisa visualmente los estantes para estimar el stock disponible. No hay un punto de reabastecimiento definido formalmente.
3. **Registro de ventas:** El vendedor anota cada venta en un cuaderno manual, incluyendo producto, cantidad y monto.
4. **Cierre del día:** Al final del día, el administrador suma manualmente las anotaciones del cuaderno para estimar el total vendido.

### 2.3 Dificultades del proceso actual

- **Desconocimiento de las ventas diarias:** La suma manual del cuaderno es lenta, propensa a errores de cálculo y no permite consultar el total en tiempo real.
- **Quiebres de stock (faltantes):** Al depender de la observación visual de los estantes, no se detecta a tiempo cuándo un producto alcanza su nivel mínimo, provocando faltantes y pérdida de ventas.
- **Falta de trazabilidad:** No existe un registro confiable con fecha y hora de cada venta, lo que impide auditar o analizar el comportamiento de ventas.
- **Descanso manual del stock:** El descuento de unidades vendidas se hace mentalmente o no se hace, generando inconsistencias entre el inventario real y lo que se cree tener.
- **Imposibilidad de identificar productos críticos:** Sin un stock mínimo definido por producto, no se puede priorizar cuáles productos reabastecer primero.

## 3. Requerimientos funcionales (RF)

### RF1. Registrar productos

El sistema debe permitir registrar un producto con los siguientes datos:

- **Código** (identificador único del producto)
- **Nombre** (descripción del producto)
- **Categoría** (clasificación del producto)
- **Precio de venta** (monto unitario vigente)
- **Stock actual** (cantidad de unidades disponibles)
- **Stock mínimo** (umbral que activa la alerta de reabastecimiento)

El sistema debe permitir editar los datos de un producto ya registrado.

> SUPUESTO: La edición de productos incluye la posibilidad de ajustar el stock actual al recibir mercadería (reposición manual), ya que no existe un módulo de compras que reste del alcance.

### RF2. Listar productos y resaltar alertas de stock

El sistema debe listar todos los productos registrados, mostrando como mínimo: código, nombre, categoría, precio de venta, stock actual y stock mínimo.

El sistema debe **resaltar visualmente** los productos cuyo stock actual es **menor o igual** al stock mínimo, de modo que el administrador identifique rápidamente los productos que requieren reabastecimiento.

### RF3. Registrar ventas de un producto

El sistema debe permitir registrar una venta con el siguiente flujo:

1. Seleccionar un producto (por código o nombre).
2. Ingresar la **cantidad** vendida de unidades.
3. El sistema toma automáticamente el **precio de venta vigente** del producto.
4. El sistema **calcula el total** de la venta: `total = precio de venta × cantidad`.
5. El sistema registra la **fecha y hora** de la venta.
6. El sistema **descuenta la cantidad vendida** del stock actual del producto.

La venta queda registrada con: producto, cantidad, precio unitario, total, fecha y hora.

### RF4. Listar las ventas del día y calcular el total vendido

El sistema debe listar las ventas registradas en el **día actual**, mostrando como mínimo: fecha y hora, producto, cantidad, precio unitario y total.

El sistema debe **calcular y mostrar el total vendido** en el día, es decir, la suma de los totales de todas las ventas del día.

> SUPUESTO: "Día" se define como el día calendario natural (00:00 a 23:59) y no un turno de trabajo. No se requiere filtrado por rango de fechas en esta versión.

## 4. Requerimientos no funcionales (RNF)

### RNF1. Seguridad de datos

El sistema debe almacenar los datos de productos y ventas de forma persistente en una base de datos. Los datos no pueden perderse ante un cierre normal del sistema o un reinicio del servidor.

> SUPUESTO: La persistencia se implementa sobre el motor de base de datos disponible en el entorno XAMPP (MySQL/MariaDB). No se requiere cifrado de datos en reposo para esta versión.

### RNF2. Integridad de datos

El sistema debe garantizar la integridad de los datos mediante:

- **Unicidad del código de producto:** No se permite registrar dos productos con el mismo código (reemplaza un identificador único generado por el sistema a partir de la clave natural del producto).
- **Integridad referencial:** Cada venta debe estar asociada a un producto existente en el catálogo. No se permite registrar una venta de un producto no registrado.
- **Validación de entrada:** El sistema debe rechazar valores inválidos (cantidades no numéricas, precios negativos, códigos vacíos) antes de persistir.

### RNF3. Atomicidad de la venta y descuento de stock

El registro de una venta y el descuento del stock del producto deben ejecutarse como una **transacción atómica**: o ambas operaciones se completan exitosamente, o ninguna se aplica. Si el descuento de stock falla, la venta no debe registrarse, y viceversa.

### RNF4. Usabilidad

La interfaz debe ser clara y operable por personal sin conocimientos técnicos, priorizando:

- Formularios simples para registro de productos y ventas.
- Listados legibles con resaltado visual evidente de las alertas de stock.
- Mensajes de error comprensibles ante validaciones fallidas.

### RNF5. Rendimiento

El sistema debe responder a las operaciones de registro y consulta (RF1 a RF4) en un tiempo razonable para un volumen propio de un minimarket de barrio. SUPUESTO: El volumen máximo esperado es de aproximadamente 500 productos y 200 ventas diarias.

### RNF6. Disponibilidad

El sistema es de uso local en el punto de venta del minimarket. SUPUESTO: La disponibilidad depende de la estabilidad del equipo local; no se requiere alta disponibilidad ni redundancia.

## 5. Reglas de negocio

Las siguientes reglas son invariantes que el sistema debe cumplir en todo momento:

| ID | Regla | Descripción |
|----|-------|-------------|
| RN1 | Cantidad vendida mayor que cero | La cantidad de unidades de una venta debe ser un entero mayor que cero. No se admiten ventas de cantidad cero o negativa. |
| RN2 | Prohibido vender más unidades que el stock | No se puede registrar una venta cuya cantidad supere el stock actual del producto. El sistema debe rechazar la operación e informar al usuario. |
| RN3 | Precio de venta no negativo | El precio de venta de un producto debe ser un valor numérico mayor o igual a cero. No se admiten precios negativos. |
| RN4 | Código de producto único | Cada producto debe tener un código único dentro del catálogo. No se permite registrar ni actualizar un producto con un código ya existente en otro producto. |
| RN5 | Venta y descuento de stock atómicos | El registro de la venta y el descuento del stock del producto forman una unidad indivisible. Ambas operaciones se completan juntas o se rechazan juntas; nunca queda un estado intermedio (venta registrada sin descontar stock, o stock descontado sin venta registrada). |

## 6. Alcance del proyecto

### 6.1 Dentro del alcance

- Registro, edición y listado de productos (RF1, RF2).
- Registro de ventas con descuento de stock (RF3).
- Listado de ventas del día con total vendido (RF4).
- Aplicación de las cinco reglas de negocio (RN1 a RN5).
- Persistencia e integridad de datos (RNF1 a RNF6).

### 6.2 Fuera del alcance

Los siguientes elementos **no** forman parte de esta versión del sistema y no deben desarrollarse:

- **Login / Autenticación de usuarios:** No se implementan credenciales ni inicio de sesión.
- **Roles y permisos:** No se implementan perfiles de usuario con accesos diferenciados.
- **Facturación electrónica:** No se emiten comprobantes fiscales ni se integran servicios tributarios.
- **Clientes:** No se gestiona información de compradores ni historial de compras por cliente.
- **Agentes conversacionales:** No se integran asistentes de IA ni interfaces de voz/chat.
- **Despliegue público / Acceso remoto:** El sistema funciona de forma local en el punto de venta; no se publica en internet ni se expone fuera del equipo.

> SUPUESTO: La conciliación bancaria, control de caja y reportes históricos por rangos de fechas también quedan fuera del alcance de esta versión.
